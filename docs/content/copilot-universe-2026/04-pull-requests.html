Writing the code is often the quick part. Then the pull request sits there. CI fails on a lint rule. You fix it, and a flaky integration test fails. You rerun it, and meanwhile someone merges to main and you've got a conflict in the lockfile. Then you wait a day for a reviewer, who leaves three comments about naming.

With agents producing more pull requests than ever (see Projects in the last lesson), that tail end becomes the bottleneck. Universe 2026 aimed two features squarely at it: Agent Merge, which gets a PR from red to merged, and upgrades to Copilot code review, which now has a deeper multi-agent level and can approve pull requests.

Key idea Code review decides whether a change is good. Agent Merge handles getting it in. Together with auto-merge and branch protection, they can carry a PR from "ready" to "merged" with a human only setting the rules.

Agent Merge: watch and fix

Agent Merge watches a pull request and fixes the blockers that stop it merging. GitHub names two kinds of blocker: failing GitHub Actions workflows and merge conflicts. It was already available in the Copilot app and VS Code. At Universe it arrived directly on pull requests on github.com.

  1. Turn it onIn the PR's merge box, choose Watch and fix.
  2. Pick what it handlesCI failures, merge conflicts or both.
  3. A blocker appearsA workflow fails, or main moves and causes a conflict.
  4. Copilot fixes itIt starts work in a cloud development environment and pushes a fix to the branch.
  5. MergeCombined with auto-merge, GitHub merges once every requirement is met.

You can also turn it on by default for all your pull requests in your Copilot settings. Agent Merge in the cloud is available on paid Copilot plans, subject to your organisation's and enterprise's policies.

Gotcha "Fix the failing check" can be done badly: deleting the test, loosening an assertion, adding a skip. Agent Merge pushes commits to your branch, so those commits deserve the same scrutiny as anything else. Keep required reviews and CODEOWNERS on the paths that matter, and look at what it changed, not just that CI went green.

Copilot code review: effort levels

Copilot code review has had effort levels since August 2026, and they work like Fusion's: you choose how much work to spend, not which model.

LevelHow it reviewsStatus
LiteSince September, an ensemble of agents rather than one agent aloneGA
BalancedThe default for new and existing repos and organisations since 2 OctoberGA
MaxSeveral independent review agents on models from different providers, reconciled by an aggregation agentPublic preview (new at Universe)

How Max works

Max is the multi-agent idea applied to review. Several review agents look at the pull request independently, deliberately using models from different providers so they don't all share the same blind spots. An aggregation agent then reconciles their findings, resolves disagreements and double-checks accuracy before producing one combined review. You get one set of comments, not five overlapping ones.

GitHub pitches Max at the riskiest changes, like authentication logic or a shared library that several services depend on. Because it does more work, it takes longer and uses more AI credits than Lite or Balanced. GitHub hasn't published how many agents a Max review uses or what a typical review costs, so try it on a few real PRs before making it a default.

Choosing and capping effort

You can pick Max for a single pull request from the Reviewers bar, or set it as the default review effort for a repository, organisation or enterprise. Each level can override the one above it.

Admins can also set a maximum effort level at the enterprise, organisation or repository level. Any level above the cap isn't available. That's the lever for stopping every PR in a busy monorepo running Max reviews.

Code review Max and approvals are available on Copilot Pro, Pro+, Max, Business and Enterprise.

Copilot approvals

Copilot code review can now approve pull requests, not just comment on them. This launched as a public preview in September and became generally available at Universe. Every review includes an approval assessment in the pull request overview comment, saying whether Copilot thinks the PR is ready to merge. When approvals are turned on, Copilot can actually approve, and that approval counts toward your repository's required approvals, just like a human's.

Three details are worth knowing:

  • Approvals are off by default. Admins turn them on at the enterprise, organisation or repository level.
  • Repository admins can choose which file paths Copilot is allowed to approve.
  • If new commits are pushed after Copilot approves, its approval is dismissed, as a human's would be, and you request a new review. That includes commits Agent Merge pushes, so a fix-up commit means a fresh review.
Should a Copilot approval count? This is a policy decision, not a technical one. A common middle ground is to let Copilot approve low-risk paths (docs, tests, generated code) using the path setting, while requiring a human CODEOWNER on sensitive ones (auth, billing, infrastructure). GitHub's own suggestion is to pair Max with approvals on the repos where a missed issue costs the most.

A note on ReviewBench

GitHub's Universe announcement said code review Max "posted the highest F1 score on ReviewBench for high-severity issues". It's worth understanding what that means and what it doesn't.

ReviewBench is a benchmark GitHub published for AI code review. It uses 219 public pull requests from 187 public repositories across 19 languages. On GitHub's leaderboard, Copilot code review at Balanced led with a 40.1% grounded F1 score. Independent coverage raised two caveats. First, Copilot itself supplied 1,185 of the 2,623 true-positive findings in the answer key, which risks favouring Copilot. Second, on a separate independent benchmark, Copilot code review ranked fifth as of early October.

None of that means the reviews are bad. It means a vendor's own benchmark is a starting point, and your own pull requests are the real test.

Putting it together

Here's what a well-guarded flow might look like for a team that's adopting both features:

  1. Agent opens a PRFrom a Project, an Automation or a person.
  2. Code review runsBalanced by default. Max on labelled or high-risk PRs, within the admin cap.
  3. Agent Merge watchesFixes CI failures and conflicts, and each push dismisses the earlier approval.
  4. Rules decideCopilot may approve only low-risk paths. Branch protection requires a human CODEOWNER elsewhere.
  5. Auto-mergeMerges once every requirement is met.

Takeaways

  • Agent Merge ("Watch and fix" in the merge box) fixes failing Actions workflows and merge conflicts in a cloud environment. It's on paid plans and can be combined with auto-merge.
  • Code review effort levels are Lite, Balanced (the default since October) and Max, a public-preview multi-agent review using models from different providers plus an aggregation agent.
  • Admins can cap the maximum review effort at the enterprise, organisation or repository level.
  • Copilot approvals are GA but off by default. They count toward required approvals, can be limited to chosen file paths, and are dismissed by any new commit.
  • Treat ReviewBench as a vendor benchmark with known caveats. Judge review quality on your own PRs, and keep human owners on sensitive paths.
