Before Universe, an agent session was tied to the client that started it. A local agent in VS Code stopped when you closed the window. A cloud session could be checked from the web, but that view differed from the editor's, and VS Code and Copilot CLI used different agent harnesses, so the same custom instructions could behave differently in each.

Universe 2026 changed this in three ways. Agents now run on one shared harness in every client. Sessions can continue after the window closes. And you can open the same live session from any Copilot client. The Copilot app also gained Projects, which coordinate several agents across several repositories.

Key point A session is no longer tied to the client that started it. One harness runs it, a background host or the cloud keeps it running, and any client can connect to it.

The shared harness

The harness is the agent loop: the code that takes your prompt, calls the model, runs tools, edits files and decides when the task is finished.

The Copilot harness is now the default for new sessions in VS Code's editor and its Agents window, and the default in JetBrains IDEs where available. Because VS Code, Copilot CLI and the Copilot app share it, agent customisations behave the same in each.

The harness is built on the Microsoft Copilot SDK, the new name for the GitHub Copilot SDK. The SDK became GA in June 2026 in six languages: Node.js/TypeScript, Python, Go, .NET, Rust and Java. GitHub says the rename reflects that the SDK now serves the agent foundation shared by Microsoft and GitHub products. It's happening in phases: the repository is moving to the Microsoft organisation and the branding and docs are being updated, but existing package names and namespaces may keep the old name during the transition.

Note If your code uses the SDK, you don't need to change anything yet. GitHub says no immediate changes are required for existing users and support is unchanged. Watch the changelog for any package rename.

Agent Host: sessions that outlive the window

In VS Code, the new Agent Host runs agent sessions in a separate process from the editor window. If you close the window or the folder, the session keeps running, and it's still there when you reopen VS Code.

It also works on another machine. VS Code's Remote SSH and dev tunnels now extend to the Agents window, so an agent can run on a separate dev box with more CPU and memory, and continue after you disconnect. To control agents on a machine from GitHub Mobile, run this in the project folder on that machine:

code agent host --github-environment

The machine and its Agent Host must stay running. If the dev box shuts down, the session stops.

GitHub also published Agent Host Protocol 1.0, an open protocol that lets other clients join live sessions and catch up after reconnecting. Client libraries exist for TypeScript, Rust, Go, Kotlin and Swift. Use it if you want to build your own tool that watches or controls agent sessions.

Cloud sessions and sandboxes

Cloud sessions run on GitHub's infrastructure, and every cloud session now runs in a cloud sandbox by default. The connected cloud experience and cloud sandboxes are generally available on paid Copilot plans. Sandboxes have no one-hour limit on total running time, and they save a snapshot when they shut down, so you can resume the session later from any client.

Billing for sandbox usage starts in November 2026 and draws from your included Actions entitlement. That entitlement is now one dollar-based pool, instead of a fixed number of runner minutes, shared by GitHub-hosted runners, cloud sandboxes and, on Team and Enterprise Cloud, larger hosted runners. Agent sessions and CI builds now spend from the same allowance. Access to the cloud experience is controlled by a Copilot setting called "Copilot in the cloud".

Session continuity means you can start a cloud session in VS Code's Agents window and continue it in the Copilot app, GitHub Mobile, github.com or Copilot CLI. All of them show the same live session. Sessions started from a Slack or Microsoft Teams message can also be continued in these clients.

  1. StartIn VS Code's Agents window: "upgrade the test framework".
  2. LeaveThe session runs in a cloud sandbox. Your laptop can sleep.
  3. CheckOn GitHub Mobile, see that the agent has a question about a config file and answer it.
  4. FinishIn the Copilot app or the CLI, open the same session and review the diff.

The Copilot app and Projects

The GitHub Copilot app is a desktop app for Windows, macOS and Linux for running agent sessions. It launched in technical preview in May 2026 and was opened to all Copilot plans in June. Each session gets its own git worktree, branch and task state, so several sessions can run in parallel without conflicting.

Projects, in public preview, are new at Universe. A project holds the context for a piece of work: several repositories, design mocks, Slack threads, meeting notes and so on. You give it a goal and choose the models and tools. Copilot runs as many agents as the work needs, tracks their progress in one place, and returns results for you to review, usually pull requests in several repos. Projects can also cover work with no code, such as a launch plan, and can have their own project automations for repeated tasks. For a task in a single repository, you can still start an ordinary session.

For example, "add rate limiting to the public API" might touch the gateway repo, a shared middleware library and the docs site. One project can run three agents for this and show all three in one view.

Warning Each agent in a project can open a pull request, so ten parallel agents can mean ten PRs to review, test and merge. Projects increase the load on reviewers, which is why the review and merge features in the next lesson matter.

Connectors and computer use

  • Copilot connectors are GitHub-verified MCP servers, in public preview on all Copilot plans. You choose a service and sign in. There is no server to find or install and no credentials to manage. A connection works across the Copilot app, Copilot CLI, VS Code, Copilot in the cloud and GitHub Mobile. Twenty-six services are available at launch, including Slack, Figma, Notion, Sentry, Linear, Atlassian Rovo, Cloudflare and Vercel. On Business and Enterprise plans, an admin must enable the Editor preview features policy and add the verified servers to any MCP allowlist.
  • Computer use lets Copilot read app content, click controls, type and move between desktop apps on macOS and Windows, including apps with no API or CLI. It's in public preview in the Copilot app and experimental in VS Code. It's off until you turn it on (in the app, Settings > Computer Use). Copilot asks for approval before controlling each app, and organisations can disable it through managed settings.

Takeaways

  • VS Code, Copilot CLI, the Copilot app and JetBrains share one Copilot harness, so customisations behave the same in each.
  • The harness is built on the Microsoft Copilot SDK, the renamed GitHub Copilot SDK. The rename is phased, and existing users don't need to change anything yet.
  • VS Code's Agent Host keeps sessions running after the window closes and can run on a remote machine, which must stay on. Agent Host Protocol 1.0 lets other clients join sessions.
  • Cloud sessions run in sandboxes, GA on paid plans. Sandbox usage is billed from November 2026 out of the shared Actions entitlement. One live session can be opened from VS Code, the app, Mobile, github.com or the CLI.
  • Projects (public preview) coordinate agents across repos and context. Connectors are verified MCP servers in public preview. Computer use is a preview you have to turn on.
