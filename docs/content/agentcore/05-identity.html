When an agent opens a pull request, reads a calendar or posts to Slack, someone has to be accountable for it. Is the agent acting as itself, with its own service account? Or is it acting on behalf of a specific user, with only that user's permissions? Getting this wrong ranges from annoying (every user sees the same calendar) to dangerous (an agent with admin rights that any user can steer).

AgentCore Identity is the part of AgentCore that answers "who is this agent, who is it acting for, and how does it get credentials?" without secrets ever passing through a prompt.

Three separate auth problems

Most identity confusion comes from mixing up three distinct layers. They're configured independently, and a mistake in any of them shows up as the same unhelpful 401 or 403.

LayerDirectionQuestion it answers
InboundCaller → agent or gatewayIs this caller allowed to invoke me, and who are they?
OutboundAgent → external APIWhat credentials does the agent use to call GitHub, Google, Jira…?
Gateway → upstreamGateway → MCP server or API targetHow does the gateway authenticate to each target?

When something returns 403, the first step is always: which of these three layers is failing?

Inbound: SigV4 or JWT

Runtimes, harnesses and gateways all accept one of two inbound methods:

  • IAM SigV4: the caller signs the request with AWS credentials. Great for backend-to-backend calls inside AWS.
  • OAuth JWT: the caller presents a token from your identity provider (Cognito, Okta, Entra ID, Auth0 or any OIDC provider). You configure a discovery URL plus allowedAudience and/or allowedClients.
The important difference Only the JWT path carries a per-user identity through to downstream tools. SigV4 tells AgentCore which AWS principal called, not which end user. If your agent needs to act on behalf of individual users (their GitHub, their Google Drive), use JWT inbound auth.

Always set allowedAudience or allowedClients. Without them, a JWT authorizer accepts any valid token from the issuer, including tokens issued for a completely different app.

The agent has its own identity too

Each agent gets a workload identity: an identity for the agent itself, separate from any user. That's what lets AgentCore say "agent X may fetch user Y's GitHub token" while agent Z can't, even for the same user.

Credential providers and the token vault

Outbound credentials live in credential providers, stored in AgentCore Identity's token vault:

  • API key providers hold a static key for APIs that only support keys.
  • OAuth2 providers hold an OAuth client ID and secret. There are ready-made configurations for popular services, GitHub and Google among them, and you can configure any other OAuth2 provider yourself.
control = boto3.client("bedrock-agentcore-control")
control.create_oauth2_credential_provider(
    name="github-provider",
    credentialProviderVendor="GithubOauth2",
    oauth2ProviderConfigInput={"githubOauth2ProviderConfig": {
        "clientId": GITHUB_CLIENT_ID,
        "clientSecret": GITHUB_CLIENT_SECRET,
    }},
)

AgentCore encrypts the secret and stores it in Secrets Manager for you. When you rotate it, go through the credential provider API (for example update-api-key-credential-provider), not Secrets Manager directly.

Getting a token in code

The Python SDK's @requires_access_token decorator does the work. Your function receives a token as an argument. The model never sees it, and it never appears in a prompt:

from bedrock_agentcore.identity.auth import requires_access_token

@requires_access_token(
    provider_name="github-provider",
    scopes=["repo"],
    auth_flow="USER_FEDERATION",
    on_auth_url=send_link_to_user,   # first time only
    callback_url=CALLBACK_URL,
)
async def list_my_repos(*, access_token: str):
    ...  # call the GitHub API with access_token

What happens the first time

  1. No token in the vault yetAgentCore generates an authorization URL and passes it to on_auth_url.
  2. Your app shows the linkThe user opens it and approves access on GitHub's own consent screen.
  3. Callback and session bindingGitHub redirects back. Your app confirms the same user who started the flow finished it.
  4. Token stored in the vaultScoped to this agent's workload identity and this user.
  5. Every later callThe token is fetched silently, and refreshed with the refresh token when it expires.

Session binding

Here's a subtle attack: a user starts the consent flow and accidentally pastes the authorization link into a team chat. Someone else clicks it and approves with their account. Now the first user's agent is holding someone else's token.

Session binding stops this. After consent, the browser returns to your callback with a session URI, and your app calls CompleteResourceTokenAuth with both that URI and the identity of the logged-in user. AgentCore only completes the exchange if it's the same user who started the flow. Authorization URLs also expire after 10 minutes.

Keeping secrets out of the model

The thread running through all of this is that credentials never belong in the model's context. If a token is in the prompt, a prompt injection can ask the model to repeat it. With Identity:

  • Tokens are injected into code (your tool function, or the gateway's outbound call), not text.
  • API keys and client secrets live in the vault, not in environment variables or system prompts.
  • Scopes limit the damage: ask for repo only if you need write access, and use a read-only scope if you don't.
Trust boundary Anyone who passes inbound auth on a Harness gets the whole session, including its shell and tools, and can send per-invocation overrides (model, skills, tools). If you put a Harness behind an app used by people you don't fully trust, validate their messages and strip or allowlist override fields in your own backend before calling InvokeHarness.

Prefer short-lived credentials

From best to worst: IAM roles (temporary, rotated automatically), then OAuth tokens (scoped, refreshable, revocable), then API keys (long-lived, all-or-nothing). Use API keys only when the target supports nothing better.

Takeaways

  • Three layers: inbound, outbound and gateway → upstream. Work out which one is failing first.
  • JWT inbound auth is needed to carry per-user identity to downstream tools. SigV4 isn't enough.
  • The token vault holds API keys, OAuth clients and per-user tokens, scoped to agent and user.
  • M2M means the agent acts as itself. USER_FEDERATION means it acts as a consenting user.
  • Session binding makes sure the user who approved access is the user who asked.
