Agents use tools to look things up and make changes. With several agents and many tools, each agent needs client code for each API, each API has its own authentication, and credentials end up in many places.

AgentCore Gateway puts all of those tools behind one endpoint. Agents talk to one endpoint using MCP (the Model Context Protocol). Behind it, Gateway connects to your Lambda functions, REST APIs, AWS services and other MCP servers, translating protocols and handling credentials on the way.

The shape of a gateway

  1. AgentSpeaks MCP: tools/list and tools/call.
  2. Inbound authorizerIs this caller allowed to use the gateway at all?
  3. Gateway + PolicyFinds the right target and checks the call against Cedar rules.
  4. Outbound credentialsIAM role, API key or OAuth token, fetched for this target.
  5. TargetLambda, OpenAPI, Smithy, API Gateway stage or MCP server.

Targets

A target is a backend the gateway connects to. Most targets are MCP targets, and the gateway runs them in aggregation mode: it acts as one virtual MCP server whose tool list is the combination of every target's tools. The agent sees one consolidated tools/list.

Target typeYou provideGood for
LambdaA function ARN plus a tool schemaCustom logic in any language
OpenAPIAn OpenAPI 3.x spec (in S3 or inline)Existing REST APIs
SmithyA Smithy modelAWS service APIs
API Gateway stageA REST API stageAPIs you already front with API Gateway
MCP serverThe server's URLRemote MCP servers, including other gateways
Integration templatesPick one and add credentialsSlack, Jira, Confluence, Salesforce, Zendesk, ServiceNow, PagerDuty and more

Beyond MCP targets there are two other categories. HTTP targets proxy traffic straight to another HTTP service, such as an agent on Runtime or an A2A agent, with no aggregation. Inference targets route model requests to one or more model providers through a single endpoint.

Note For OpenAPI targets, the operation descriptions in your spec become the tool descriptions the model reads. A spec full of summary: "getThing" produces tools the model won't know how to use. Write them for an LLM reader.

Tool names

Since many targets are merged into one list, Gateway prefixes each tool with its target name, separated by three underscores. A process_refund operation on a target called RefundTarget becomes RefundTarget___process_refund. You'll see these names again in Policy.

Semantic tool search

A model given 300 tool definitions is slower, costs more and chooses tools less accurately. Gateway can offer semantic tool search as a built-in tool: the agent describes what it's trying to do and gets back only the relevant tools, across every target type.

Two directions of auth

A gateway has inbound auth (who may call the gateway) and outbound auth (how the gateway calls each target), configured completely separately.

Inbound: who can use the gateway?

  • OAuth (JWT): callers present a token from your identity provider (Cognito, Okta, Entra ID, Auth0…).
  • IAM (SigV4): callers sign requests with AWS credentials.
  • Authenticate only: the token is validated, and the decision about what's allowed is left to the target.
  • No authorization: development and testing only.

Outbound: how does the gateway reach the target?

  • Lambda and Smithy targets use the gateway's IAM execution role. Scope it to exactly the functions and APIs needed.
  • OpenAPI and MCP server targets use an AgentCore Identity credential provider (an API key or OAuth client), SigV4 signing, or nothing for public endpoints.
Warning Create the credential provider before the target that uses it. Creating the target first fails with "credential provider not found". The provider stores the secret in Secrets Manager for you, so don't create that secret yourself.

Targets go through statuses as they're created. Wait for READY. An MCP server target that needs a human to log in (three-legged OAuth) sits in CREATE_PENDING_AUTH until someone completes consent. MCP server targets can also be SYNCHRONIZING while Gateway refreshes their tool list.

Calling a gateway from an agent

To your agent, a gateway is a remote MCP server. With Strands it looks like this:

from strands import Agent
from strands.tools.mcp import MCPClient
from mcp.client.streamable_http import streamablehttp_client

gateway = MCPClient(lambda: streamablehttp_client(
    GATEWAY_URL,
    headers={"Authorization": f"Bearer {access_token}"},
))

with gateway:
    agent = Agent(tools=gateway.list_tools_sync())
    agent("Refund order 1182, it arrived damaged")

With a Harness, add a tool of type agentcore_gateway with the gateway's ARN.

Policy: rules enforced outside the model

A model doesn't always follow its system prompt. It can be persuaded to ignore "never refund more than £1,000" by an instruction hidden in an email it was asked to summarise. Policy in AgentCore puts hard rules outside the model, at the gateway, where every tool call is checked before it reaches the target.

Policies are written in Cedar, AWS's open-source authorization language:

permit(
  principal,
  action == AgentCore::Action::"RefundTarget___process_refund",
  resource == AgentCore::Gateway::"<gateway-arn>"
)
when {
  context.input.amount < 1000
};

Read it as: allow the process_refund tool on this gateway when the amount argument is under 1000. Cedar evaluates policies like this:

  • If no permit matches, the request is denied (deny by default).
  • A matching forbid always wins over any permit.
  • Conditions can look at who's calling, which tool it is, and the actual tool arguments (context.input).

Writing policies in plain English

You don't have to write Cedar by hand. Describe the rule in natural language and AgentCore generates the Cedar for you (agentcore gateway policy generate in the CLI). The generated policy is checked in three steps:

  1. An LLM translates your description into Cedar.
  2. A Cedar schema is generated from your gateway's real tool definitions, and the policy is validated against it, so it can't reference tools or arguments that don't exist.
  3. Cedar Analysis uses automated reasoning to catch policies that allow everything, deny everything or can never match, and checks how the whole policy set interacts when you attach it.
Key point Policy is deterministic. It evaluates rules rather than asking a model whether a call looks acceptable. A prompt injection can change what the model does, but not how the rule is evaluated.

Takeaways

  • Gateway gives agents one MCP endpoint over many targets: Lambda, OpenAPI, Smithy, API Gateway, MCP servers and integration templates.
  • Tools are named Target___tool. Semantic search helps when there are many of them.
  • Inbound auth (JWT, IAM) and outbound auth (IAM role, credential provider) are configured separately. Create credential providers first.
  • Policy checks every tool call with Cedar: deny by default, and forbid beats permit.
