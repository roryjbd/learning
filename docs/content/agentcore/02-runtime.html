AgentCore Runtime is where your agent's code actually runs. It's serverless: you hand it your agent, either as a container image or as a bundle of Python code, and it handles scaling, isolation and routing. It's also the foundation the Harness runs on, so even if you never write a Runtime agent yourself, it helps to understand how it behaves.

Sessions are the unit of everything

The single most important idea in Runtime is the session. Every invocation carries a runtimeSessionId, and Runtime gives each distinct session its own dedicated microVM, with its own kernel, memory and filesystem.

  • Call again with the same session ID and you land in the same microVM. Files the agent wrote, packages it installed and variables in memory are all still there.
  • Use a different session ID and you get a completely separate, isolated environment. One user's session can never see another's files.

The session ID must be at least 33 characters. A standard UUID with hyphens (36 characters) works. Over HTTP it travels in the X-Amzn-Bedrock-AgentCore-Runtime-Session-Id header.

Why microVMs? Agents run model-generated actions like shell commands, file edits and code. Hardware-level isolation per session means a prompt-injected agent in one session can't reach data in another. It's the same kind of isolation that separates Lambda functions, applied per conversation.

How long a session lives

Sessions don't last forever. On the default microVM compute type there are two clocks:

SettingDefaultWhat happens
idleRuntimeSessionTimeout15 minutesNo activity for this long and the microVM is terminated.
maxLifetime8 hoursThe microVM is terminated regardless of activity.

Both are configurable in the runtime's lifecycle configuration, from 60 seconds up to 8 hours (28,800 seconds), and the idle timeout must be no larger than the max lifetime.

When a session's microVM is terminated, the session ID isn't dead. The next call with that ID simply provisions a fresh microVM. Anything on the local disk is gone, unless you've set up persistent storage.

Keeping files across restarts

Imagine a coding agent that spends twenty minutes cloning a repo and installing dependencies. You go for lunch, the idle timeout fires, and when you come back it has to start from scratch. Managed session storage (in preview at the time of writing) fixes this. You declare a mount path when you create the runtime:

aws bedrock-agentcore-control create-agent-runtime \
  ... \
  --filesystem-configurations '[{"sessionStorage": {"mountPath": "/mnt/workspace"}}]'

Anything written under /mnt/workspace survives stop and resume for that session ID. The path must be directly under /mnt (one level deep), and there's a limit of 1 GB per session. For bigger or shared data you can mount EFS or S3 Files instead.

Running commands directly

Sometimes you don't want the model involved at all. "Run the test suite" is deterministic, so routing it through an LLM as a tool call just adds tokens, latency and a chance of it going wrong. InvokeAgentRuntimeCommand runs a shell command inside an existing session, in the same container with the same filesystem as the agent, and streams back stdout, stderr and the exit code.

So a single session can mix InvokeAgentRuntime ("agent, fix this bug") with InvokeAgentRuntimeCommand (npm test). You'll see this pattern again in the coding-agent lesson.

You choose the compute type when you create the runtime and can't change it afterwards. For most agents, microVMs are the right default.

Pick a protocol

Runtime can host four kinds of server. Choose before you build, because each has a different contract:

ProtocolPort and endpointsUse when
HTTP8080: GET /ping, POST /invocations (JSON or SSE), optional /wsMost agents. Request in, response (or stream) out.
MCP8000: POST /mcp (streamable HTTP)You're hosting a tool server for other agents.
A2A9000: agent card at /.well-known/agent-card.json, JSON-RPC on /Agents talking directly to other agents.
AG-UI8080: SSE events on /invocationsStreaming rich agent events straight to a front end.

Not sure? Start with HTTP.

The container contract

If you deploy a container, it has to follow a few rules:

  • ARM64 (Graviton). An x86 image won't start on microVMs. Build with --platform linux/arm64.
  • A health check on /ping (for every protocol except MCP) that returns {"status": "Healthy"}, or "HealthyBusy" while the agent is doing background work so Runtime knows not to treat it as idle.
  • Logs to stdout and stderr. They go to CloudWatch automatically.
  • Handle SIGTERM so you shut down cleanly when a session ends.

You rarely write this plumbing by hand. The Python SDK's BedrockAgentCoreApp gives you /ping and /invocations for free:

from bedrock_agentcore.runtime import BedrockAgentCoreApp
from strands import Agent

app = BedrockAgentCoreApp()
agent = Agent(system_prompt="You are a helpful assistant.")

@app.entrypoint
def invoke(payload, context):
    prompt = payload.get("prompt", "Hello")
    return {"response": str(agent(prompt))}

if __name__ == "__main__":
    app.run()

Notice that agent is created at module level, outside the handler. Because a session keeps its microVM, that same Agent object, with its conversation history, is reused across turns in a session.

Container or direct code?

With container deployment you build an ARM64 image, push it to ECR and point the runtime at it. Maximum control, but slower to iterate. With direct code deployment you upload your Python code and dependencies as a bundle and AgentCore runs it, with no Dockerfile or ECR. Use that for fast iteration. The agentcore CLI handles either.

Versions and endpoints

Every update to a runtime creates a new immutable version. Endpoints are named pointers to a version, and they're what callers actually invoke. To roll back, you point the endpoint at an older version, with no rebuild.

Locking it down

  • Execution role: the IAM role the agent runs as. Scope it to exactly what that agent needs, and give each agent its own role.
  • Inbound auth: callers use either IAM (SigV4) or an OAuth JWT authorizer. Never ship a production runtime that anyone can call.
  • Network: PUBLIC mode is fine for experiments. Use VPC mode in production to reach private resources and control egress.
  • No secrets in environment variables. Anyone with GetAgentRuntime can read them. Use Secrets Manager or AgentCore Identity (lesson 5).

What you pay for

On microVMs you're billed per second for the CPU and memory your session actually consumes. The important detail for agents is that CPU usage drops to zero while the agent is waiting on I/O: model responses, tool calls, database queries. Since most of an agent's life is spent waiting on a model, that's a big difference from paying for a server that's always on. Memory has a 128 MB billing minimum, and in Runtime v2 idle memory is reclaimed automatically.

Watch out Billing runs from when the microVM is ready until the session terminates, including idle time before the timeout fires. A shorter idleRuntimeSessionTimeout saves money for chatty, short-lived sessions.

Takeaways

  • Session ID → dedicated microVM. Same ID, same environment. Different ID, total isolation.
  • Sessions end after 15 minutes idle or 8 hours total by default. Use session storage under /mnt to keep files.
  • Protocols are HTTP (default), MCP for tool servers, A2A for agent-to-agent, and AG-UI for front ends.
  • Containers must be ARM64 and answer /ping. BedrockAgentCoreApp does this for you.
  • You pay for consumed CPU and memory, and CPU is free while waiting on I/O.
