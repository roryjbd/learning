Models are stateless. Every call starts from nothing, and the only "memory" an agent has is whatever you put back into the prompt. That's fine for one turn, but real agents need to remember two very different kinds of thing:

  • What just happened: the last few messages in this conversation, the tool call that just failed, the file the user mentioned two turns ago.
  • What it has learned: this user prefers Python, their company has three offices, last week we decided to use Postgres.

AgentCore Memory handles both, as short-term and long-term memory, inside one managed resource.

The three IDs

Everything in Memory is organised by three identifiers. Get these straight and the rest falls into place.

IDWhat it isExample
memoryIdThe memory resource itself. You usually have one per agent or application.SupportMemory-8f3k2j9d1a
actorIdWho the memory is about: a user, another agent, or a system.user-4821
sessionIdOne conversation or interaction period.2026-11-03-morning-chat

Short-term memory is scoped by actor + session, so each user's conversations are kept separate. Long-term memory is usually scoped by actor, so what's learned in one session is available in the next.

Security actorId is a trust boundary. Derive it from the authenticated user on your server side. Never let the caller pass in whatever actorId they like, or they can read someone else's memories.

Short-term memory: events

Short-term memory is a log of events. Each one is immutable and stored synchronously, so you can read it back straight away. There are two kinds:

  • Conversational events have a role (USER, ASSISTANT, TOOL…) and content. These are your chat transcript.
  • Blob events hold arbitrary data, such as checkpoints or serialised agent state. They're stored, but they aren't used for long-term extraction.
import time, boto3
mem = boto3.client("bedrock-agentcore")

# Record a turn
mem.create_event(
    memoryId=MEMORY_ID,
    actorId="user-4821",
    sessionId=session_id,
    eventTimestamp=int(time.time() * 1000),
    payload=[
        {"conversational": {"role": "USER",
            "content": {"text": "I prefer Python for scripts"}}},
        {"conversational": {"role": "ASSISTANT",
            "content": {"text": "Noted, I'll use Python."}}},
    ],
)

# Load recent context at the start of the next turn
recent = mem.list_events(
    memoryId=MEMORY_ID, actorId="user-4821",
    sessionId=session_id, maxResults=10,
)

When you create the memory resource you set eventExpiryDuration, the number of days raw events are kept. Short-term data is high volume and loses value quickly, so don't keep it longer than you need.

Long-term memory: strategies

Raw transcripts are a terrible long-term memory. They're huge, repetitive and mostly noise. Long-term memory works by extracting the useful parts. You attach one or more strategies to the memory resource, and AgentCore reads new conversational events asynchronously in the background and turns them into compact memory records.

StrategyExtractsExample record
SemanticFacts and knowledge"The customer's company has 500 employees across Seattle, Austin and Boston."
User preferenceLikes, choices and styles"Prefers detailed technical explanations. Uses Python."
SummaryA running summary of a session"Asked about enterprise pricing, discussed timeline, wants a demo."
EpisodicEpisodes (what happened and how it turned out), plus reflections across episodes"Deploy failed on missing IAM permission. Fixed by adding iam:PassRole."

Extraction also consolidates: if a user says they've switched from Python to Go, the preference record is updated rather than a contradicting record being added next to it.

If the built-ins don't fit your domain you have two escape hatches:

  • Custom strategies let you pick the model and override the extraction and consolidation prompts. For example, "only extract facts about the user's infrastructure".
  • Self-managed strategies hand the work to you. AgentCore notifies you via SNS when there's new data, and your own pipeline (say, a Lambda) does the extraction and writes records back.

Namespaces

Each strategy writes its records into a namespace, a path built from a template:

strategies = [
  {"semanticMemoryStrategy": {
      "name": "facts",
      "namespaceTemplate": ["/users/{actorId}/facts/"]}},
  {"userPreferenceMemoryStrategy": {
      "name": "prefs",
      "namespaceTemplate": ["/users/{actorId}/preferences/"]}},
  {"summaryMemoryStrategy": {
      "name": "summaries",
      "namespaceTemplate": ["/users/{actorId}/{sessionId}/summary/"]}},
]

{actorId} and {sessionId} are filled in from the event. Namespaces do two jobs: they isolate users from each other, and they let you scope retrieval. Ask only the preferences namespace when you're deciding how to format an answer, or only the facts namespace when you're answering a question.

Getting memories back out

APIUse it to
RetrieveMemoryRecordsSemantic search: "find records relevant to this query". This is the one you call during a conversation.
ListMemoryRecordsEnumerate everything in a namespace, for a "here's what I remember about you" screen or an audit.
GetMemoryRecord / DeleteMemoryRecordWork on a single record, for example when a user asks you to forget something.
 
hits = mem.retrieve_memory_records(
    memoryId=MEMORY_ID,
    namespace="/users/user-4821/facts/",
    searchCriteria={"searchQuery": user_message, "topK": 5},
)

Passing the user's message straight in as searchQuery works when it maps naturally to stored memories ("what's my budget?"). For vague requests ("help me plan my next trip") it often helps to have the model write a better search query first, at the cost of an extra model call.

Putting it in the loop

A typical turn with memory looks like this:

  1. Load short-term contextListEvents for the last N turns of this session.
  2. Recall long-term contextRetrieveMemoryRecords against the relevant namespaces.
  3. Call the modelWith recent turns and retrieved records added to the prompt.
  4. Save the turnCreateEvent with the user message and the reply. Extraction runs later, in the background.

You often don't write this yourself:

  • Strands Agents has an AgentCore Memory session manager that does the loading and saving for you.
  • A Harness takes a memory setting (managed memory, your own memory ARN, or disabled) and an actorId per invocation, and wires up short- and long-term memory automatically.
Gotcha Extraction is asynchronous. A fact mentioned a moment ago is in short-term events immediately, but it may not be a retrievable long-term record yet. Don't write tests that create an event and instantly expect RetrieveMemoryRecords to find it.

Designing it well

  • Memory sits on the hot path. Retrieval latency is paid on every turn, and sometimes on every reasoning step. Retrieve once per turn where you can, and keep topK small.
  • Different memories deserve different lifetimes. Expire raw events and session summaries first. Keep distilled facts and preferences much longer.
  • Encrypt it. Memory holds conversation content, which often contains personal data. Use a customer-managed KMS key for regulated workloads.
  • Scope IAM tightly. Grant the specific Memory actions an agent needs, not bedrock-agentcore:*.

Takeaways

  • Short-term memory is immutable events, scoped by actor and session, readable immediately.
  • Long-term memory is records extracted asynchronously by strategies: semantic, user preference, summary and episodic, or your own.
  • Namespaces like /users/{actorId}/facts/ isolate users and focus retrieval.
  • Use RetrieveMemoryRecords to recall what's relevant and ListMemoryRecords to enumerate.
  • Treat actorId as security-sensitive and set it on the server.
