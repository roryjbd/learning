Getting an agent working on your laptop is the easy part. A model, a system prompt, a couple of tools and a loop, and you have a demo in an afternoon. The hard part is everything after that. Where does it run when a thousand people use it at once? How does it remember a user from last week? How does it call your internal APIs without you pasting keys into prompts? How do you stop it doing something it shouldn't, and how do you find out what it actually did?

Amazon Bedrock AgentCore is AWS's answer to that second half. It isn't an agent framework and it doesn't write your prompts. It's a set of managed services, each one solving a specific production problem, that you can use together or one at a time.

Key idea AgentCore is framework-agnostic and model-agnostic. You can bring Strands Agents, LangGraph, CrewAI or your own hand-rolled loop, and call Bedrock models, OpenAI, Gemini or anything LiteLLM supports. AgentCore provides the infrastructure around the agent, not the agent itself.

What's in the box

Here's the full set of services. You don't need to memorise them yet. Later lessons go deep on the first five.

RuntimeServerless hosting for agents and tools. Each session gets its own isolated microVM.
HarnessA managed agent loop. Describe the agent as config, no code or container.
MemoryShort-term conversation events plus long-term facts, preferences and summaries.
GatewayTurns APIs, Lambdas and MCP servers into one MCP tool endpoint.
IdentityInbound auth, plus a token vault so agents can act on a user's behalf.
PolicyCedar rules that check every tool call going through Gateway.
Code InterpreterA sandbox where the agent can run Python, JS or TS safely.
BrowserA managed headless browser the agent can drive.
ObservabilityOpenTelemetry traces and metrics into CloudWatch.
EvaluationsLLM-as-a-judge scoring of agent quality from traces.
RegistryA catalogue of agents, MCP servers, tools and skills across your org.
PaymentsLets agents pay for x402-protected APIs and content with microtransactions.

The services are modular. Each has its own API, so you can mix and match. An agent running on ECS or Lambda can still use AgentCore Memory, a Gateway can serve tools to an agent hosted somewhere else entirely, and so on. Using Runtime doesn't lock you into the rest.

Following one request through

The easiest way to see how the pieces fit is to follow a single user message all the way through a fully kitted-out agent:

  1. Your app calls the agentIt sends a message and a session ID. The caller proves who it is with either AWS SigV4 or an OAuth JWT (Identity, inbound).
  2. Runtime routes it to a sessionThe same session ID always lands in the same isolated microVM, so files and in-process state survive between turns.
  3. The agent loop thinksYour code (or the Harness) calls a model, maybe loading recent turns and relevant long-term facts from Memory first.
  4. It needs a toolThe agent calls Gateway over MCP. Policy checks the call against Cedar rules before anything happens.
  5. Gateway calls the real systemA Lambda, a REST API or another MCP server, using credentials fetched from Identity's token vault, never from the prompt.
  6. The answer streams backThe turn is written to Memory as events, and traces go to CloudWatch for Observability and Evaluations.

Keep this flow in your head. Every later lesson zooms into one of those boxes.

Harness or Runtime?

This is the first real decision you make, and it's simpler than it looks. Both run on the same underlying Runtime infrastructure. They differ in how much of the agent you write yourself.

HarnessRuntime
You provideConfiguration onlyAgent code, as a container or a code bundle
Agent loopManaged for you (built on Strands)You write it, in any framework
Change the model or add a toolConfig change, no redeployCode change and redeploy
Best forGetting a capable agent running fastCustom control flow, graphs and workflows, bidirectional streaming

A Harness is declared as a model, a system prompt, tools, skills, memory and limits. Each session still runs in its own microVM with a filesystem and a shell, so it's more powerful than it sounds. It comes with built-in shell and file_operations tools, and you can opt in to Gateway, remote MCP servers, Code Interpreter and Browser. It can even load Agent Skills (the SKILL.md format) from AWS, a Git repo, S3 or the session's filesystem.

Many fields can also be overridden per invocation: model, system prompt, tools, skills and limits. That makes A/B testing a new model or prompt trivial.

Rule of thumb Start with a Harness. Drop down to Runtime when configuration stops being enough: you need a specific framework, a non-loop workflow, custom hooks, or full control over every step.

Control plane and data plane

Like most AWS services, AgentCore splits its API in two, and knowing which is which saves a lot of confusion when you read SDK code:

  • bedrock-agentcore-control is the control plane. You use it to create and manage things: runtimes, endpoints, harnesses, memories, gateways, credential providers and policies.
  • bedrock-agentcore is the data plane. You use it to do things: invoke an agent runtime or harness, write and read memory events, retrieve memory records, start Code Interpreter sessions.
  • Each Gateway also gets its own endpoint, which agents talk to over MCP.
import boto3

control = boto3.client("bedrock-agentcore-control")  # create / configure
data = boto3.client("bedrock-agentcore")             # invoke / read / write

How you actually build with it

There are three main ways in, and you'll likely use more than one:

  • The AgentCore CLI (agentcore, installed from npm). agentcore create scaffolds a project, agentcore dev runs it locally with an inspector, agentcore deploy ships it, and agentcore invoke talks to it. This is the fastest path.
  • The Python SDK (bedrock-agentcore). Its BedrockAgentCoreApp wraps your agent so it speaks the Runtime contract, and it has helpers for Memory, Identity and the built-in tools. There's a TypeScript SDK too.
  • Infrastructure as code. CloudFormation resources and CDK constructs (aws_bedrockagentcore) exist for runtimes, gateways, memories and credential providers.
Heads up If you've seen the older Bedrock Agents service (action groups, bedrock-agent), that's a different product. It's now in maintenance mode and closed to new customers. AWS points new agent work at AgentCore, and there's a migration path from classic agents to a Harness.

Why not just use Lambda or ECS?

You can, and plenty of people do. But agents have an awkward shape for general-purpose compute:

  • They're long-running and bursty. A single turn might take seconds or many minutes, mostly spent waiting on a model. Runtime doesn't charge CPU while the agent waits on I/O like model responses or tool calls.
  • They're stateful. A coding agent wants its checked-out repo to still be there on the next message. Runtime keeps a session's microVM alive for up to 8 hours.
  • They run untrusted, model-generated actions. Hardware-level isolation per session means one user's agent can't see another's files or memory.
  • They need identity plumbing that's painful to build yourself, such as OAuth consent flows, token refresh and per-user scoping.

Takeaways

  • AgentCore is the production layer around an agent: hosting, memory, tools, identity, policy, observability. It isn't a framework.
  • Services are modular, so use only the pieces you need.
  • Harness means a config-defined agent with a managed loop. Runtime means you bring the code.
  • The control plane (bedrock-agentcore-control) creates things. The data plane (bedrock-agentcore) uses them.
