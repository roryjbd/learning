Time to put it all together. The goal is an agent you can hand a GitHub issue to, something like "fix #42 in acme/api", that will:

  1. read the issue,
  2. clone the repo into its own workspace,
  3. find and edit the right files,
  4. run the tests until they pass,
  5. push a branch and open a pull request for a human to review.

Along the way you'll use almost everything from the previous lessons. This lesson is about the design: which piece does which job, and why.

The architecture

  1. Your app (or a Slack bot, or a GitHub webhook)Authenticates the user with a JWT and calls the agent with a session ID per task.
  2. Runtime session (microVM)Strands agent with file and shell tools. The repo lives in /mnt/workspace via session storage.
  3. IdentityA GitHub OAuth credential provider. The user consents once (USER_FEDERATION) and the agent works as them.
  4. Gateway + Policy (optional)GitHub's MCP server as a target for issue and PR tools. Cedar forbids merging and deleting.
  5. MemoryRemembers each repo's conventions: test commands, code style, things that broke before.
  6. ObservabilityTraces of every model and tool call, so you can see why it changed what it changed.

Decision 1: Harness or Runtime?

A Harness already has a shell, file tools and a microVM per session, so it's tempting. And it works well if every GitHub action goes through APIs: reading issues, reading and writing files and opening PRs via GitHub's MCP server behind a gateway.

But a real coding agent wants to git clone a private repo and run the test suite locally. That means the shell needs a GitHub credential, and the safest way to get a user's token into a git command without it ever entering the model's context is code: a tool function decorated with @requires_access_token. So this lesson uses Runtime with a Strands agent. It's still a small amount of code.

Rule of thumb If the agent only needs GitHub's API, use a Harness with a gateway. If it needs a real working copy and a local toolchain, use Runtime, where your code controls the credentials.

Decision 2: How does it talk to GitHub?

There are two complementary routes, and many teams use both:

For the code below we'll go direct, and add a gateway policy afterwards.

Step 1: Set up GitHub access

  1. Register an OAuth app (or a GitHub App) in GitHub. Set its callback URL to the one AgentCore Identity gives you for the provider.
  2. Create the credential provider in AgentCore: 
    control.create_oauth2_credential_provider(
    name="github-provider",
    credentialProviderVendor="GithubOauth2",
    oauth2ProviderConfigInput={"githubOauth2ProviderConfig": {
        "clientId": CLIENT_ID, "clientSecret": CLIENT_SECRET}},
)
  3. Give the runtime JWT inbound auth, so the user's identity flows through to the token vault (lesson 5).
Scope it down A classic OAuth app's repo scope covers every repo the user can access. A GitHub App installed on only the repos you choose is much tighter. Either way, turn on branch protection for main in GitHub itself, so even a confused agent can only ever open a PR.

Step 2: The agent

import subprocess, httpx
from strands import Agent, tool
from strands_tools import file_read, editor
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from bedrock_agentcore.identity.auth import requires_access_token

app = BedrockAgentCoreApp()
WORK = "/mnt/workspace"          # session storage: survives restarts

@requires_access_token(
    provider_name="github-provider",
    scopes=["repo"],
    auth_flow="USER_FEDERATION",
    on_auth_url=send_link_to_user,   # stream the consent link to your UI
    callback_url=CALLBACK_URL,
)
async def gh_token(*, access_token: str) -> str:
    return access_token

def sh(cmd: list[str], cwd: str = WORK) -> str:
    r = subprocess.run(cmd, cwd=cwd, capture_output=True, text=True, timeout=900)
    return f"exit={r.returncode}\n{r.stdout[-3000:]}\n{r.stderr[-3000:]}"

@tool
async def read_issue(repo: str, number: int) -> str:
    """Fetch a GitHub issue's title and body. repo is 'owner/name'."""
    token = await gh_token()
    r = httpx.get(f"https://api.github.com/repos/{repo}/issues/{number}",
                  headers={"Authorization": f"Bearer {token}"})
    issue = r.json()
    return f"#{number}: {issue['title']}\n\n{issue['body']}"

@tool
async def clone_repo(repo: str) -> str:
    """Clone owner/name into the workspace (or pull if already there)."""
    token = await gh_token()
    name = repo.split("/")[1]
    url = f"https://x-access-token:{token}@github.com/{repo}.git"
    out = sh(["git", "clone", url, name])
    # Don't leave the token sitting in .git/config
    sh(["git", "remote", "set-url", "origin",
        f"https://github.com/{repo}.git"], cwd=f"{WORK}/{name}")
    return out.replace(token, "***")

@tool
def run(command: str, repo_dir: str) -> str:
    """Run a shell command (e.g. the test suite) inside the repo."""
    return sh(["bash", "-lc", command], cwd=f"{WORK}/{repo_dir}")

@tool
async def open_pull_request(repo: str, branch: str, title: str, body: str) -> str:
    """Commit all changes to a new branch, push it, and open a PR."""
    token = await gh_token()
    d = f"{WORK}/{repo.split('/')[1]}"
    sh(["git", "checkout", "-b", branch], cwd=d)
    sh(["git", "add", "-A"], cwd=d)
    sh(["git", "-c", "user.name=fix-agent", "-c", "user.email=fix-agent@users.noreply.github.com",
        "commit", "-m", title], cwd=d)
    sh(["git", "push", f"https://x-access-token:{token}@github.com/{repo}.git",
        branch], cwd=d)
    r = httpx.post(f"https://api.github.com/repos/{repo}/pulls",
                   headers={"Authorization": f"Bearer {token}"},
                   json={"title": title, "head": branch, "base": "main", "body": body})
    return r.json().get("html_url", r.text)

agent = Agent(
    system_prompt=(
        "You fix GitHub issues. Read the issue, clone the repo, find the cause, "
        "make the smallest change that fixes it, and run the tests until they pass. "
        "Never push to main. Finish by opening a pull request that explains the fix."
    ),
    tools=[read_issue, clone_repo, file_read, editor, run, open_pull_request],
)

@app.entrypoint
async def invoke(payload, context):
    result = await agent.invoke_async(payload["prompt"])
    return {"result": str(result)}

if __name__ == "__main__":
    app.run()

A few things to notice:

  • The token never reaches the model. It's fetched inside tool code, used, and scrubbed from any output that goes back to the model.
  • agent lives at module level, so follow-ups in the same session ("also update the changelog") keep the conversation and the cloned repo.
  • The code decides how branches work, not the model. The model picks the branch name and PR text, and the push always goes to that branch.

Step 3: Deploy it

Use the CLI. It packages the code (direct code deployment, or an ARM64 container), creates the runtime and wires up the execution role:

agentcore create        # scaffold, choose Python + HTTP
agentcore dev           # try it locally first
agentcore deploy

Then set what matters for this workload:

  • Session storage at /mnt/workspace, so a lunch break doesn't throw away the clone and the installed dependencies.
  • Lifecycle: an idle timeout long enough for a slow test suite, and a max lifetime well under 8 hours.
  • VPC mode if it needs to reach private package registries.

Step 4: One session per task

import json, uuid, boto3
data = boto3.client("bedrock-agentcore")
session = f"fix-acme-api-42-{uuid.uuid4()}"   # >= 33 chars

data.invoke_agent_runtime(
    agentRuntimeArn=RUNTIME_ARN,
    runtimeSessionId=session,
    payload=json.dumps({"prompt": "Fix issue #42 in acme/api"}),
)

Each task gets its own microVM, so two issues being fixed at once can't interfere with each other.

Trust, but verify

The agent will say the tests pass. Don't take its word for it. Because InvokeAgentRuntimeCommand runs a command in the same session with the same filesystem, your orchestrator can independently run the test command in /mnt/workspace/api and check the exit code itself, with no model involved. And GitHub's own CI runs on the PR anyway.

Step 5: Guardrails with Gateway and Policy

If you also give the agent GitHub's hosted MCP server through a gateway (say, a target named GitHub, for richer issue and PR tools), Policy can draw hard lines. Here's an example, assuming the server exposes a merge_pull_request tool:

forbid(
  principal,
  action == AgentCore::Action::"GitHub___merge_pull_request",
  resource
);

Because forbid always beats permit, no prompt, issue text or README instruction can get the agent to merge its own work. That matters here, because issue bodies are untrusted input. Anyone who can file an issue can try to inject instructions.

Step 6: Make it learn each repo

Add Memory with the repo as the actor, for example actorId = "repo:acme/api", with semantic and episodic strategies:

  • Semantic facts: "tests run with make test", "uses pnpm, not npm".
  • Episodes: "last time the auth tests failed it was a missing env var in .env.test".

Before each task, retrieve from /repos/repo:acme/api/… and add the results to the prompt. The agent gets faster on repos it has seen before.

Step 7: Watch it

  • Traces (OpenTelemetry into CloudWatch) show every model call, tool call and tool result. That's how you answer "why did it edit that file?"
  • Metrics: invocations, latency, errors and session counts come for free. Token usage needs ADOT instrumentation.
  • Evaluations can score finished runs with an LLM judge, which helps you notice when a model or prompt change makes things worse.

The checklist

  • Runtime, Strands agent, session storage at /mnt/workspace.
  • JWT inbound auth, GitHub OAuth provider, USER_FEDERATION, narrow scopes or a GitHub App.
  • Tokens used only inside tool code and scrubbed from output.
  • One session per task. Verify tests yourself with InvokeAgentRuntimeCommand.
  • Branch protection in GitHub, plus Cedar forbid on merge and delete.
  • Memory keyed by repo. Traces and alarms on.
  • The agent opens PRs. A human merges them.
